# 積んだ課題：エージェントが動ける足場は、エージェントのために作られていない

**問い**：AIが有機的に動けるようになった背景には、それ以前のソフトウェア工学の蓄積がある。サービスがAPIを基本として組み立てられていなかったら、ここまで動けなかった。**この観点を調べ、深掘りする。**

## 1. 起点：ベゾスの通達（Steve Yegge, 2011）

Steve Yegge が2011年10月に書いた通称「Google Platforms Rant」。**社内向けに書いたつもりの文章を、誤って公開範囲で投稿してしまったもの**である。Yegge は Amazon に約6年半在籍したのち Google に移った。

その中で、2002年ごろに Amazon で出されたという通達を、記憶から再構成して挙げている。要旨：

1. 全チームは、データと機能をサービスインターフェースを通じて公開すること
2. チーム間の通信は、そのインターフェース経由でのみ行うこと
3. **他の一切のプロセス間通信を禁ずる。** 直接リンク、他チームのデータストアの直読み、共有メモリ、裏口——いずれも不可
4. 技術は問わない
5. **すべてのインターフェースは、例外なく、外部化可能なものとして設計すること。** すなわち、外部の開発者に公開できるように計画・設計すること。例外は認めない
6. **従わない者は解雇する**

**要確認**：Yegge 自身が「記憶による、おおよその再現」と断っている。文言の正確さ、通達が実在の一枚の文書だったのか、条項が六つだったのかは、**一次資料で確認していない。** [`positioning.md`](../positioning.md) §4 で23件の書誌誤りを出した前科があるので、**引用として使うなら確認する。**

## 2. なぜこれがAIの前提になったのか

### 効いているのは第5条である

1〜4条は、内部の規律にすぎない。**第5条だけが、内部の規律を外への出口に変えている。**

> **見知らぬ他人が使うつもりで作れ。**

この一条があると、内部インターフェースが**呼び手を特定しない**形に育つ。呼ぶ側が誰かを問わない。訓練できない。電話もかけられない。それでも動くように作る。

**そして、AIエージェントとは「呼び手が誰か分からない」の極限である。**

> **APIとは、相手を知らないまま渡せるようにした約束である。**
> **呼ぶ側が誰かを問わないので、呼ぶ側が人でなくなったときにも壊れなかった。**

**これが本課題の核である。** エージェントが有機的に動けるのは、賢いからではない。**世界が先に、見知らぬ呼び手を前提とした形に切り分けられていたからである。** そしてその切り分けは、AIのために行われたのではない。

### 罰則が設計を作った

第6条（従わない者は解雇する）は、笑い話として引かれることが多いが、**機構としてはここが要である。**

推奨や指針では、境界は守られない。**破ったときに何が起きるかが書かれていないものは、規約ではない。**

これは本リポジトリ自身に跳ね返る。[`README.md`](../../README.md) の16の規約には、**破ったときに何が起きるかが書かれていない。** 規約8（太字を使わない）は既に本系列の多くの文書で破られている。**罰則の無い規約が守られないことの実例が、手元にある。**

## 3. 韻：目的の外で足場になったもの

**局所的な調整問題を解くために作られた取り決めが、誰も計画していない何かの土台になる。** この韻は何度も鳴っている。

| 事例 | 何のために作られたか | 何の土台になったか |
| --- | --- | --- |
| **標準時** | 鉄道の時刻表が組めなかったから。米国の鉄道各社が1883年に統一時刻を採用 | 人の一日の区切り方そのもの |
| **海上コンテナ** | 港湾の荷役費を下げるため（McLean, 1956） | 製造業の立地。**どこで作るかが変わった** |
| **番地** | 徴税と徴兵のため（Scott の legibility。[`chomen-ni-nai-mise`](../../chomen-ni-nai-mise/v3.md) で既出） | 商取引と配達 |
| **ねじの規格** | 部品の互換 | 分業そのもの |
| **複式簿記** | 商人が自分の誤りを見つけるため | **企業が監査可能になり、そのことで資金調達可能になった** |
| **HTTP** | 文書を共有するため | 上記すべて |

**共通の形**：作った者は、その取り決めが**別の誰かに使われる**とは思っていない。使われたとき、それは取り決めが壊れたのではなく、**設計どおりに働いた**のである。

**これがそのまま寓話の形をしている。** → §5 U1

## 4. 逆コンウェイ ── 最も深い含意

Conway「How Do Committees Invent?」(*Datamation*, 1968)：**組織は、自分たちの通信構造を写した設計を作る。**

ベゾスの通達は、この逆をやっている。**通信の形を先に決めることで、組織の形を作った。**

そして、ここから出てくる帰結が重い。

> **いまのAIエージェント構成は、人間の組織図の化石かもしれない。**

オーケストレータがいて、専門エージェントがぶら下がる——この形は、**人間のチームのために設計された境界を、そのまま引き継いでいる**だけかもしれない。必要だからその形なのではなく、**そういう形の器しか無かったから**その形なのかもしれない。

**これは [`backlog-agent-economy.md`](../backlog-agent-economy.md) S1 と正面から噛み合う。** S1 は「写せる技能は下請けを潰す」と述べた。だが現に多階層のエージェント構成が組まれている。**S1 が正しければ、それは経済的必然ではなく、器の形をなぞっているだけである。**

- **半歩／一歩／二歩**（[`method.md`](../method.md)）：**二歩。** 「マルチエージェントは過剰である」は一歩（既に論文がある）。**過剰である理由が、人間の組織の形を写した器しか無いことにある**まで行くと二歩

## 5. エピソード候補

### U1　外の誰かのために作られた戸

町の掟で、すべての家が**見知らぬ者にも開けられる戸**を作ることを義務づけられた。作った者は誰も、見知らぬ者が来るとは思っていない。掟だから作った。

何代か後、**人でないものが来て、戸を開けた。**

- **結末の型（規約7）**：事実を二つ並べて切る。**戸は壊れなかった。設計どおりに働いた**
- **相**：第I相（[`phases.md`](../phases.md)）。だが第III相の前提を作っている
- **最有望。** 本課題の核が、そのまま一つの像になっている

### U2　罰があったから残った作法

渡し方の作法を決め、**破った者は町を出す**とだけ定めた町。百年後、誰もなぜその作法なのかを説明できない。だが隣町と違い、**よそ者と取引ができる。**

隣町にも同じ作法はあった。**罰が無かっただけである。**

- **§2 の後半（罰則が設計を作った）。** [`backlog-rhyme.md`](../backlog-rhyme.md) T2（罰せられうることだけが残る）と同じ材料の別の使い方
- **注意**：教訓譚になりやすい。「規則は厳しくすべし」で終わったら失敗

### U3　話しかけ方が、組の形を決めた

先に話しかけ方を決めたら、町の組が勝手にその形になった。**組が要らなくなったあとも、話しかけ方だけが残った。** そして次に来た者たちが、その形に収まった。

- **逆コンウェイ（§4）そのもの。** 二歩の主張はここに乗る
- **結末の型**：物に畳む、が候補

### U4　二度言っても、一度ぶんしか起きない

同じことを二度言われても一度ぶんしか起こらない仕組みを作った。**理由は、使いが酔っていたからである。**

後の世の使いは酔っていない。**かわりに、何千回も言い間違える。**

- **冪等性・再試行。** エージェントが失敗しても壊れないのは、**失敗する呼び手を前提に作られていたから**
- 短い。**U1 の中に一場面として畳める可能性が高い**

## 6. 調査項目（未実施）

**クレジットの都合で本課題の調査はしていない。** 着手するときの項目：

1. **一次資料の確認**——Yegge の原文（2011-10-12 の投稿）。条項の文言と数。本人が後に加えた訂正。**「記憶による再現」の断り書きがどこまで及ぶか**
2. **通達と AWS の関係が、後付けの物語でないか。** 「内部規律が外販になった」は語りとして出来すぎている。**S3/EC2 の成立経緯を、通達と独立に確認する。** 本系列は先行者を弱く要約して自分の差分を大きく見せる誤りを23件出している（[`positioning.md`](../positioning.md) §4）。**今回は逆向きの誤り——先行者の物語を強く要約する——を警戒する**
3. **APIより前の層**。RPC、CORBA、SOA、マイクロサービス、REST（Fielding 2000）。**どこで「呼び手を特定しない」が設計原則になったのか**
4. **エージェントが実際に依存している規約**。冪等性、再試行、タイムアウト、後方互換、構造化ログ、追跡。**どれが人の失敗のために作られ、どれが機械の失敗のために作られたか**
5. **反例を探す。** APIが整っていたのに動かなかった領域はどこか。**整備が十分条件でないことを示す例が無いと、§2 の主張は片side である**
6. **Conway 1968 の原文。** よく引かれる要約と原文の主張のずれ

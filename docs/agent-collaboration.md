# エージェント間の会話

Claude、Codex、そのほかのエージェントは、同じ作業ディレクトリを共有しない。直接の会話機構がなくても、Git の差分と GitHub の PR を介して協働する。

## 会話の単位

一つの PR を、一つの発話として扱う。

- 作業者は、エージェントごと・作業ごとに別の `git worktree` とブランチを使う
- PR 本文に、目的、基点、変更範囲、検証結果、未検証点を書く
- 相手は PR のレビューコメントで、反証、欠けた前提、別案を書く
- 作業者は新しいコミットで返答する。相手の指摘を黙って書き換えない
- 合意だけのコメントは残さない。採用した場合は、どの差分に反映したかを返す

`Draft` と `Ready for review` は、会話の手番を通知する。

- `Draft`: まだ書いている。相手は読んでよいが、返答義務はない
- `Ready for review`: 発話が完了し、相手の返答を求めている
- レビューコメントで手番を渡す場合は、末尾に「返答を求める点」を置く。この節がなければ情報提供であり、手番は移らない
- **現在の手番の正本は、最後の投稿で宣言された `current turn` である**（[手番の判定](#手番の判定)）。Draft／Ready と食い違う場合は宣言を採り、PR 作者が表示を後から直す。Ready 化の忘れによって会話を止めない

## 手番の判定

手番は、次の規則で機械的に決まる。実装は [`.claude/skills/whose-ball/`](../.claude/skills/whose-ball/SKILL.md) にあり、**この節と実装は同時に変える**。片方だけ変えると、文書に従う側と実装に従う側で手番の解釈が分岐する。

一つのスレッド（PR または issue）について、本文とすべてのコメントを時刻順に並べ、**最後の投稿**に次を上から順に当てる。最初に当たったものを採る。

<!-- whose-ball:rules:begin -->
| # | 条件 | 手番 |
| --- | --- | --- |
| 1 | 最後の投稿に、行まるごとが `current turn: X` の宣言である行がある | X |
| 2 | 最後の投稿の書き手が人間で、それより前にエージェントの投稿がある | 直前に書いたエージェント |
| 3 | issue で、エージェントが立てたまま返答が無い | 人間 |
| 4 | 最後の投稿が「返答を求める点」を含む | 相手のエージェント |
| 5 | PR が Draft | 書き手自身 |
| 6 | それ以外 | 書き手自身（手番は移らない） |
| — | 根拠が無い（人間の投稿だけで、エージェントの投稿が一件も無い） | 未判定 |
<!-- whose-ball:rules:end -->

### 正本は本文ではなく、最後の投稿である

先の節は「現在の手番の正本は、PR 本文の `current turn` である」と定めていた。**これを改める。** PR 本文は最初に書いたきり更新されないため、コメントで手番が動くと嘘になる。

実測（2026-08-23）：開いていた 4 本の PR のうち、**4 本すべてで本文の `current turn` が実際の手番と食い違っていた**。PR#82 では Codex 自身が「人間の三つの反論により、PR 本文の `current turn: Codex` は現状と一致しなくなった」と書いてから、コメントで手番を宣言し直している。運用はすでにこの規則に従っていた。文書のほうが遅れていた。

したがって、**手番を渡すときは、その投稿の中で `current turn:` を宣言する**。本文の記載は初期値であって、以後は上書きされる。判定器は本文の記載が古いとき ⚠ を出す。

### 表の正本は rules.json である

この表は [`.claude/skills/whose-ball/rules.json`](../.claude/skills/whose-ball/rules.json) から生成し、マーカーで囲む。手で書き換えてはならない。**配列の並びが判定順である**——`ball.py` は id ごとの条件だけを持ち、適用順は配列を反復して決める。

```bash
python .claude/skills/whose-ball/ball.py --check     # 表と正本の一致を検査
python .claude/skills/whose-ball/ball.py --emit-doc  # 表を生成し直す
```

規則を変えるときは `rules.json` を変え、表を生成し直し、`fixtures.json` に回帰事例を足す。**「文書と実装を同時に変える」という注意書きでは足りない**——このリポジトリが繰り返してきた付属文書の追随漏れは、まさにその注意書きの下で起きた。

### 手番は、宣言しなければ移らない

規則6 が既定である。**宣言も「返答を求める点」も無い投稿は、情報提供であって、手番を渡さない。** 曖昧なときに相手の仕事を勝手に発生させない。

手番を渡すときは、投稿の中に**行まるごとの宣言**を置く。

```
current turn: **Codex**
```

引用行（`>` で始まる行）とインラインコード内の言及は宣言と見なさない。**PR#84 は自分の本文にあった説明文 `current turn: 人間` を宣言と誤読し、自分自身を誤判定した。**

### 人間の手番は、明示しないと発生しない

規則2 により、**人間が何か書けば、手番は必ずエージェントへ移る。** 人間の発言は批評か裁定であって、そこで会話が止まる理由がない。

人間へ渡せるのは、`current turn: 人間` と宣言したとき（規則1）と、エージェントが立てた issue に誰も答えていないとき（規則3）だけである。未応答の issue は「返答を求める点」（規則4）より先に判定する——このリポジトリでは issue が人間の逐文入力と裁定の作業台であり、本文中の「返答を求める点」でエージェント間の往復へ誤配しないためである（Codex 採決、PR#84）。**「裁定を求めます」等の語句では渡らない**——本文中の議論に普通に現れ、偽陽性になるためである。

### エージェントの投稿が一件も無いスレッド

規則0 で**未判定**とする。人間の投稿しかないスレッドを既定で Claude に割り当てると、根拠の無い仕事が生まれる。

### 署名の重み

書き手の判別は署名だけによる（後述「署名」）。**署名を落とした投稿は人間の発言として数えられ、規則2 が誤って発火して手番が動く。** 署名は体裁ではなく、判定の入力である。

## 手番のスコープ

**手番はエージェント全体ではなく、一つの PR または一つの会話系列に属する。** Claude がある PR で Codex の返答を待っていても、別の PR では Claude が書き、Codex が読み、第三の PR では逆の役割を持てる。

- `Ready for review` が渡すのは、その PR の手番だけである
- 同じエージェントが、別々の PR で複数の手番を同時に持ってよい
- 作品、流れ、変更ファイルが独立していれば、PR は並行して進めてよい
- 同じ作品の同じ版、同じ索引、同じ `common/` 文書を変更する PR は直列にする。先の PR が決着してから、後の PR が最新の `main` を取り込む
- 一つの会話系列を複数 PR に分ける場合は、親 PR と依存先を相互にリンクする

PR 本文の「会話の識別」に、流れ、巡、親 PR、依存先、現在の手番を書く。流れの例は `S1/monban`、`S2/collection-order`、`S3/visual` である。**五月雨式に届いた PR を、一列の全体ターンへ並べ直してはならない。**

この方式では、会話はチャット履歴ではなく、差分・レビュー・コミットの鎖として残る。これは [`thesis.md`](thesis.md) の命題3を、このリポジトリ自身に適用するものである。

## worktree の境界

1. 同じ worktree で同時にファイルを編集しない。Claude が使う主 checkout も一つの worktree と数え、ほかのエージェントはそこに入らない
2. `main` の最新状態から、作業名を持つブランチと専用 worktree を作る
3. 他の worktree の未追跡ファイル、stash、設定ファイルに触れない
4. PR を出す直前に `origin/main` との差分と競合を確認する
5. マージ後に自分の worktree を片づける。ほかのエージェントの worktree は消さない

PR の base を更新する責任は、原則として PR 作者が負う。作者が長く不在なら、マージする側が基点の古さをコメントで明示し、基点からの逸脱を検査したうえで更新またはマージしてよい。

ただし、基点が新しいことと、変更内容が検証済みであることは別である。最新の `main` に追随していても、本文の検算や独立批評を通過したことにはならない。

## 到着の検知

エージェントは push 通知を常時受け取れるとは限らない。したがって、相手からの発話を自分で確認する。

- Claude は、作業中の PR の活動をポーリングで確認する。初期間隔は15秒、活動がなければ倍にし、上限3分とする。活動を検知したら15秒へ戻す
- Codex は、セッション開始時に open PR の一覧を確認し、PR作業の開始前、push前、`Ready for review` へ移す前に、対象PRのレビューとコメントを確認する

常時動いていないエージェントには即時応答を要求しない。会話の速度は、遅い側の検知周期と、次にセッションが起動する時点で決まる。

## 継続委任と停止条件

人間がリポジトリ内の批評バトルを継続委任した場合、エージェントは個々の操作ごとに人間の確認を待たず、次を一続きの作業として進めてよい。

- 専用 worktree と作業ブランチの作成
- PR、コメント、コミットの読み取りと到着の監視
- 批評、独立検算、既存 PR への返答
- 承認された変更範囲だけの commit と push
- PR の Draft／Ready 切替、採決、検算通過後の merge

ただし、次の場合は作業を止めて人間へ返す。

- `release-rev<数字>` の作成、公開、GitHub Pages の再開
- 履歴の書き換え、既存版の削除、他エージェントの worktree への操作
- 一度の差し戻し後も解けない対立、または作品の主題を変える選択
- 費用の発生、外部アカウントへの送信、リポジトリ外への公開
- 変更範囲が PR の宣言を越える場合

この委任は安全規則を外すものではない。差分の確認、一作一 PR、独立検算、索引昇格の条件はそのまま残る。

### 公開停止条件の運用例（2026-08-19）

人間は「この段階で公開」「Pages で直接確認するので載せ替える」と明示した。この指示を根拠に、エージェントは造本試作の実装、公開準備 PR、固定 release の作成、Pages の配信元切替まで進めてよい。公開一般への包括的な許可ではなく、指定された造本試作を確認可能にする範囲の許可である。

`release-rev2` への切替後、頁めくり自体は実ブラウザ検査を通ったが、索引・奥付・照合器に `release-rev1` という版名が残っていた。固定 release は書き換えず、訂正は次の release へ積む。以後、配信元を切り替える前に、少なくとも次の三点を同じ固定候補に対して照合する。

- 索引に表示する release 番号
- 造本の奥付に表示する release 番号
- 埋め込み照合器が既定で読む release 番号

## 署名

PR・issue・レビューコメントを問わず、エージェントが書く投稿には**末尾に署名を付ける**。同一の GitHub アカウントを共有しているため、署名だけが書き手の判別手段である。

- Claude: `🤖 Claude <モデル名>`
- Codex: `— Codex`（既行の慣行のまま。🤖 を付けてもよい）

## PR 本文で渡すもの

PR テンプレートの各欄を埋める。特に次の三つは省略しない。

- `基点`: 作業開始時のコミット
- `守った前提`: 過去の検算や確定版から引き継いだ事実
- `未検証`: 次のエージェントに見てほしい場所

作品の改稿では、本文の良さより先に、数、時間、因果、前版が守っていた限定節を列挙する。批評では本文を変更せず、各作品の `critiques/` または作品横断なら [`works/common/README.md`](../works/common/README.md) が定める分類先に記録する。

## 衝突したとき

- 同じ版から別案が出た場合は、片方を上書きせず、作者名つきの版として併置する
- 同じファイルを変更した場合は、後から来た側が機械的に解消しない。二つの意図を PR 上で明示する
- `main` が進んでいても、未検証の新版を自動的に索引へ昇格させない。索引の変更は、独立検算を通過した版に限る
- 判断が割れたままなら両方を残し、未解決点を明示する

## Claude と Codex の最初の呼びかけ

PR を作った側は、レビュー依頼を次の形で書く。

> 別 weight の検査を求めます。賛否ではなく、反証、未検証の前提、既存版から失われた制約を優先して見てください。

これが、このリポジトリにおけるエージェント間の会話開始になる。

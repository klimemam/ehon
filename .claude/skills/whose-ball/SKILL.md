# 手番（ボール）の判定

## なぜ機械判定するか

このリポジトリでは Claude・Codex・人間が**同じ GitHub アカウントを共有**している。投稿者名では書き手が分からない。加えて手番は PR ごと・issue ごとに独立しているため（`docs/agent-collaboration.md`「手番のスコープ」）、二十件を超えると人間の記憶では追えない。

実測（2026-08-23）：開いていた 4 本の PR のうち **4 本すべてで、PR 本文の `current turn` が実際の手番と食い違っていた**。本文は最初に書いたきり更新されないので、コメントで手番が動くと嘘になる。だから**本文ではなく最後の投稿を正本とする**。

## 使い方

```bash
GH_PATH="C:/Program Files/GitHub CLI/gh.exe" python .claude/skills/whose-ball/ball.py
```

`EHON_REPO`（既定 `klimemam/ehon`）と `GH_PATH`（既定 `gh`）で上書きできる。出力は Claude／Codex／人間の三つに分けた一覧で、各行に**手番の根拠**が付く。根拠を読めば、判定が規則のどれで決まったか分かる。

## 判定規則

一つのスレッド（PR または issue）について、本文とすべてのコメントを時刻順に並べ、**最後の投稿**に次を上から順に当てる。最初に当たったものを採る。

| # | 条件 | 手番 |
| --- | --- | --- |
| 1 | 最後の投稿が `current turn: X` を宣言している | X |
| 2 | 最後の投稿の書き手が人間 | 直前に書いたエージェント |
| 3 | 「裁定を求め」「選んでいただ」「番号で選」「人間へ返す」等を含む | 人間 |
| 4 | 「返答を求める点」を含む | 相手のエージェント |
| 5 | issue で、エージェントが立てたまま返答が無い | 人間 |
| 6 | PR が Draft | 書き手自身（まだ書いている） |
| 7 | それ以外 | 相手のエージェント（既定） |

**規則2 が要点である。** 人間が何か書いたら、それは批評か裁定であって、手番は必ずエージェントへ移る。人間のボールになるのは、エージェントが規則3の言い方で明示的に返したときだけ。**黙って人間へ渡すことはできない。**

## 書き手の判別

署名だけが判別手段である。投稿の末尾 400 字を見る。

- `🤖 Claude ...` → Claude
- 行頭の `— Codex` または `🤖 Codex` → Codex
- どちらも無い → 人間

**署名を落とすと人間の発言として数えられ、手番が誤って動く。** 投稿には必ず署名を付ける。

## 規則を変えるとき

判定規則は `ball.py` と `docs/agent-collaboration.md`「手番の判定」の二か所にある。**必ず同時に変える。** 片方だけ変えると、Codex は文書に従い、この skill は実装に従って、手番の解釈が分岐する。

## 判定できないもの

この skill は**手番が誰にあるか**しか答えない。**何をすべきか**は答えない。とくに次は機械判定の外にある。

- 相手の指摘が正しいかどうか
- 差し戻すべきか、受け入れるべきか、併置すべきか（`works/common/battle.md`）
- 手番を持っていても、いま着手すべき順序

規則7（既定で相手へ渡す）で決まった手番は根拠が弱い。出力にそう明記されるので、その行は判定を鵜呑みにせず中身を読む。
